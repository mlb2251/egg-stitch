TL;DR. The best-first search's seen-set had an experimental egraph side built on egg (over a frozen-var language, deciding dedup since it was the default decider). I replaced that egraph with a slotted e-graph (memoryleak47/slotted-egraphs), where a pattern's metavariables become slots, so alpha-equivalent patterns (the same shape with variables permuted — the blow-up that commutativity/associativity create) collapse natively, no rules needed. The corpus egraph is untouched (still egg), as requested. On nuts-bolts the new backend reproduces the egg results bit-for-bit: identical expansions (1185), identical egraph hits (657), identical final library (1.77×). It is slower in wall-clock here (slotted saturation is less optimised, and this domain has no commutativity so the alpha-equivalence advantage can't show — exactly as you predicted). It still beats the no-seen run. On a purpose-built commutative domain (§6½) the sharing does show: it cuts the search ~3.8× (82 vs 311 expansions) with an identical answer. All lib tests pass, including 7 in the new module that pin the encoding's semantics and the sharing.

1. What the seen-set is, and what I touched

Best-first abstraction search (src/best_first.rs) expands partial patterns. Many successors are redundant: the same search state reached by a different route. The seen-set (SeenTracker in src/search.rs) dedups them. It actually carried three parallel structures:

  • map — a hash map Pattern → freeze-mask with subset-domination. Cheap, syntactic.
  • dom_map — a never-evicted shadow of map for measuring how much domination buys.
  • the egraph side — each (pattern, freeze-mask) encoded as a term and looked up / inserted in an egg e-graph, with the domain rewrite rules (DSRs) run to saturation so dedup is modulo DSR-equivalence. This side was the default decider (--seen-egraph-decides, on by default).

This task replaces only the egraph side — the egg EGraph over the frozen-var language OpWithFrozenVar — with a slotted e-graph. The map/dom_map shadows stay (they're independent, cheap, and give the comparison the stats print). The corpus e-graph stays egg.

Why slotted, concretely. In the egg encoding a metavariable ?#k is a distinct constant leaf Var(k). So (+ ?#0 ?#1) and (+ ?#1 ?#0) are different egg terms; they only merge if a commutativity rule is present and saturated. In a slotted e-graph a metavariable is a slot, and the e-graph canonicalises terms up to a bijective renaming of slots — so those two collapse to one e-class at insertion time, with no rules. That native alpha-equivalence is the whole point: in domains with commutativity/associativity the search emits a pattern's variables in every order, and slotted folds them for free.

2. The encoding

The new backend is src/seen_slotted.rs. It defines one slotted Language and a handful of conversions. A pattern + its freeze mask becomes a slotted term like this:

  pattern          (T ?#0 ?#1)                with ?#0 frozen, ?#1 free
  slotted term     ($root$ (T (fpv $0) (pv $1)))
  • Non-frozen ?#k → a free slot, materialised as the leaf e-node (pv $k). Reuse of ?#k reuses slot $k, so variable sharing is preserved.
  • Frozen ?#k → (fpv $k) — the same slot $k under a distinct head. (See the judgement call below for why this is the right shape.)
  • Every operator → Op(symbol, children) — one variable-arity node carrying the operator name as a Symbol and its children as a Vec<AppliedId>. This is why one language covers an entire corpus whose operator set is only known at runtime.
  • The whole term is wrapped in Op($root$, [term]). add_expr interns every subterm, so without the wrapper a membership lookup would hit a pattern that merely occurs inside a larger inserted one. With it, a hit means the whole pattern was inserted as a top-level state. (This is the same trick the egg side used with its Root sentinel.)

DSRs are lifted onto this language (lift_rules_from_file) and run to saturation, so the e-graph dedups modulo DSR-equivalence on top of the alpha-equivalence it folds for free — matching the egg side's behaviour. Dedup itself is a membership check: build the $root$-wrapped term, and lookup_rec_expr it; present ⇒ skip, absent ⇒ insert (and, per the batch schedule, saturate).

3. Judgement calls

Frozen variables: (fpv $k), not renamed names and not a single tag chosen

You floated two options: distinct names like fx1, fx2, or a wrapper like (frozen x1). I used a wrapper-style head over the same slot: (fpv $k). The reasoning is a small case analysis of what "the same search state" must mean for frozen vars:

  • Frozenness must be structural so a frozen position never collapses with a free one: (T (fpv $0) (pv $1)) ≠ (T (pv $0) (fpv $1)) — different child is pinned, genuinely different states. The distinct head fpv vs pv gives exactly this.
  • Frozenness must still travel with the slot under renaming so two states that differ only by relabelling collapse: (T (fpv $0) (pv $1)) = (T (fpv $1) (pv $0)) (rename $0↔$1). Keeping the slot inside the fpv node gives this for free via slotted alpha-equivalence.
  • A frozen var must keep its identity for reuse / distinctness: (T ?#0 ?#0) (one frozen var twice) ≠ (T ?#0 ?#1) (two frozen vars). Because the slot lives inside the node, (T (fpv $0) (fpv $0)) ≠ (T (fpv $0) (fpv $1)) — preserved.

A single shared frozen tag (no slot) fails the third point; distinct names like fx1, fx2 fail the second (they'd need re-canonicalising to collapse relabellings). The slot-bearing distinct head satisfies all three. Tests relabelled_frozen_collapses and frozen_vs_free_stays_distinct pin this.

No binders — free slots at top level chosen

You noted the encoding "might look like a bunch of binds up at the top, or possibly no binds at all if free variables are allowed with no binder." Slotted e-graphs allow exactly that: an e-class simply has a set of public (free) slots; no lam/let binder is required to introduce them. So I use bare free slots and the $root$ wrapper just passes them through. No binders anywhere — the more convenient option, and it's what makes the alpha-equivalence "just happen" at add/lookup time.

Reused variables: nothing special needed confirmed

You expected reuse to be a non-issue, and it is. Index k maps to slot $k deterministically, so every occurrence of ?#k is the same slot and the sharing is preserved structurally. No special handling.

Membership, not e-class equality, is the dedup test important

A subtlety worth recording: in a slotted e-graph, (T (pv $0) (pv $1)) and (T (pv $1) (pv $0)) do share an e-class, but add_expr returns AppliedIds that bind the free slots in opposite orders, so an eg.eq(...) on those two applied-ids is false (they're different as applied terms). The operation the seen-set actually wants is "is an equivalent term present?", i.e. lookup_rec_expr on the canonicalised shape, which correctly returns hit. So contains() uses membership, never applied-id equality. (I learned this the hard way — see bug #2.)

Keep running the DSRs in the seen-egraph chosen

One could hope alpha-equivalence alone replaces the DSRs. It doesn't, in general: commutativity over structured arguments ((+ ?#0 (f ?#1)) ↔ (+ (f ?#1) ?#0)) is a real merge that alpha-equivalence does not make. And on nuts-bolts specifically the rules aren't commutativity at all — they're 7 scale-1 identities — so all the dedup there is DSR-driven. To faithfully replace the egg side (and to match its numbers) the slotted egraph runs the lifted DSRs to saturation, same as before. The alpha-equivalence is a bonus that simply doesn't fire on this no-commutativity domain.

Hand-written Language instead of define_language! chosen

The library's define_language! macro fixes each variant's arity and ties it to one operator-name string. A corpus has arbitrarily many operators of arbitrary arity, known only at runtime. So Op is a single variable-arity (Symbol, Vec<AppliedId>) variant, and I hand-write the Language impl — which is just the per-child chaining the macro would have generated, plus a from_syntax that dispatches on the head string (pv/fpv → slot leaves, anything else → operator).

Lift rules by string, skip what doesn't parse limitation noted

The rule file format (name: lhs => rhs, // comments, <=> bidirectional) and the slotted pattern syntax both use ?x metavariables and the same S-expression operator form, so rules lift almost verbatim. A rule whose sides don't parse as SeenLang — most importantly a lambda-calc rule using de-Bruijn $i, which the slotted parser reads as a slot — is skipped with a warning rather than crashing the run, and the count is surfaced. constant_folding directives are likewise skipped. This is the one real fidelity gap vs. the egg lifter (see §7); it does not affect nuts-bolts, whose rules are plain op-children rewrites.

Kept the whole SeenTracker interface and all CLI flags chosen

Every --seen-egraph-* flag still means what it meant: saturate, saturate-every, saturate-dynamic, decides. The dynamic batch-tuner's "did this flush dedup anything?" signal is reproduced faithfully — a freshly-inserted $root$ class that becomes multinode after a flush must have merged (by congruence) with another inserted root, since no rule mentions $root$. I dropped only --seen-egraph-node-limit from this path (the slotted runner is iteration-bounded, not node-bounded) and the egg-only search/apply/rebuild time breakdown from the audit print.

4. Bugs I hit (and fixed)

Bug #1 — node ordering. caused total search collapse
First run terminated after 18 expansions instead of 1185 — the egraph was reporting almost everything as already-seen. The dump was damning: (T ?#0 ?#1) was converting to just ($root$ (pv $1)) — operator and first child gone. Cause: I built pos_to_var from the pattern's own var-id table, but a pattern is stored as a RevExpr (root at index 0); converting it to an egg RecExpr reverses the node array and remaps child ids, so those ids no longer line up. Fix: detect variable leaves intrinsically via discriminant().as_var() and recover the index from a Var → k map — exactly what the old egg converter did. With that, every pattern converts to its full structure and the false hits vanish.
Bug #2 — eg.eq vs membership. While validating the encoding, my "alpha-equivalent patterns collapse" test failed on eg.eq(add(a), add(b)) even though the two were the same e-class. The returned applied-ids bind the shared free slots in opposite orders, so they differ as applied terms. The dedup the seen-set performs is membership (lookup_rec_expr), which canonicalises and correctly hits — so the test was wrong, not the encoding. Rewrote the tests around contains(), the real operation.

6. A domain where alpha-equivalence is the point (lambda-calc smoke test)

To check the lambda-calc path didn't regress, I ran basic-apps/multi-arg-assoc with its app-arith.rewrites — which are commutativity and associativity (plus_commut, plus_assoc, plus_merge, in curried @ form, no de-Bruijn, so all 6 lift cleanly). It saturates and returns a result: 468 expansions, 378 egraph hits, 4108 genuine inserts. This is the exact shape of redundancy slotted exists to fold.

This is also where the slotted saturation cost bites hardest: associativity+commutativity build large e-classes and the per-insert saturation ran ~2.7 s each (32 s total). The library's own benchmarks note assoc/comm add-chains can blow up. Two future levers for these domains: (a) drop the commutativity rule entirely and let native alpha-equivalence subsume it (a pattern's reordered variables are alpha-equivalent without any rule), and (b) the incremental-saturation work sketched in docs/seen_egraph_incremental_plan.html. Out of scope here — the goal was correctness, and that holds.

Three things to read off this:

  • The sharing fires: the slotted egraph explores 82 states vs 311 — it recognises the AC-reordered/reassociated partial patterns as one search state instead of re-expanding each ordering. The audit confirms the collapse directly: 411 genuine inserts → 303 distinct DSR-classes (108 reordered patterns folded).
  • The sharing is correct: all three settings find the identical abstraction (+ (+ (+ ?#0 ?#1) ?#2) ?#3) (the clean 4-way sum template). Folding the reorderings does not change the answer — it isn't over-merging distinct states.
  • It's the egraph's doing, not the map's: "map" and "no seen-set" both sit at 311 — the alpha-canonical pattern map catches nothing extra here (the search already emits patterns in canonical variable-numbering). The entire win is the e-graph folding the AC equivalence class, which is exactly what was moved onto slotted.

Honest caveat on wall-clock: this corpus is tiny, so the slotted saturation overhead (~0.5 s) actually exceeds the raw search it saves (no-seen runs in ~0.01 s here). The expansion count is the blow-up metric that matters — it is what explodes combinatorially as the corpus grows, and that is what the sharing flattens. Full timing breakdown in §7.

Mechanism-level: comm is folded by alpha (free), assoc by the DSR (on demand), nothing spurious

Two unit tests in src/seen_slotted.rs pin the equivalence exactly — that it shares what it should and nothing more:

  • commutativity_reordering_folds_via_alpha — with no rules at all, inserting (+ ?#0 ?#1) already makes (+ ?#1 ?#0) a member. Pure variable reordering is folded structurally by the slot encoding, exactly the slotted-specific win (the egg encoding needed a commutativity rule for this).
  • associativity_needs_dsr_not_alpha — alpha alone must not reassociate (a leaf slot can't be renamed into a subtree), and the test asserts (+ (+ ?#0 ?#1) ?#2) does not become (+ ?#0 (+ ?#1 ?#2)) with no rule; with the assoc DSR saturated, it does. This is the "right" boundary: comm for free, assoc on demand, no spurious merges.

7. Wall-clock: is it faster? (no — here's the full breakdown)

Worth being blunt: on both examples the slotted seen-set is not a wall-clock win. The alpha-equivalence advantage is real at the level of expansions (it folds the AC sharing — 82 vs 311), but that does not translate to wall-clock on these inputs. There are two different "slower than what?" questions with two different answers.

comm-demo (14 programs): slotted-seen vs no-seen — slower, because expansions here are nearly free

configexpansionstotalof which: egraph saturationeverything else
no seen-set3110.010 s— (no egraph)0.010 s
slotted (egraph decides)820.451 s0.431 s (96%)~0.020 s
map decides (egraph as shadow)3110.829 s0.771 s (93%)~0.058 s

The seen-set did its job — 82 vs 311 expansions — but look at what an expansion costs here: 0.010 s / 311 ≈ 32 µs. The corpus is tiny, so each expansion is nearly free; cutting 229 of them saves only ~0.007 s. To save that, the slotted egraph spent 0.43 s saturating the DSRs after inserts. Net ~0.44 s slower. The seen-set is an asymptotic optimization — it trades egraph bookkeeping for fewer expansions, and that only pays off once expansions are expensive enough. On a 14-program toy they aren't. (The "map decides" row is the worst case: it still builds and saturates the egraph as a shadow, so it pays the 0.77 s and runs all 311 expansions.)

nuts-bolts (250 programs): the seen-set does beat no-seen — but slotted is 3× the egg it replaced

configexpansionstotalegraph saturation
no seen-set10000 (budget)2.24 s—
slotted seen-set11850.92 s0.43 s
egg seen-set (before)11850.32 s0.012 s

Here the corpus is big enough that expansions are ~7× more expensive (2.24 s / 10000 ≈ 224 µs each) and there is a real blow-up (10000 → 1185). So the seen-set earns its keep: slotted-seen (0.92 s) is faster than no-seen (2.24 s). But it is 3× slower than the egg seen-set — identical 11 saturation flushes, identical dedup, but slotted saturation took 0.43 s vs egg's 0.012 s (~36× slower per flush).

Two root causes.
  1. The slotted e-graph's saturation engine is much slower than egg's (~36× per flush on nuts-bolts). It's a young library — a naive fixpoint loop, less-optimised e-matching/rebuild — and, like the egg version, it re-saturates the whole accumulated egraph on every flush (the cost docs/seen_egraph_incremental_plan.html targets). This is an implementation-maturity gap, not fundamental.
  2. The seen-set only beats no-seen when expansions are expensive and the blow-up is large. comm-demo has neither (tiny corpus, ~32 µs expansions), so the egraph overhead dominates no matter how good the engine is.

So what was delivered is a correct, behaviour-identical replacement that demonstrably folds the AC sharing — not a faster one. Levers that would flip the wall-clock trade, none done here: drop the commutativity rule and lean on native alpha (fewer/cheaper rules for the egraph to saturate); batch or incrementalise saturation; or run on a corpus large enough that the expansion blow-up dwarfs the egraph cost.

8. Limitations / things to know

  • Lambda-calc rules with de-Bruijn $i are skipped (the slotted parser reads $i as a slot). The run prints how many rules were dropped. For such domains the seen-egraph dedups by alpha-equivalence only, not by those rewrites. nuts-bolts and basic-apps are unaffected.
  • Reserved heads pv, fpv, $root$ would collide with a corpus operator spelled identically. None exist in the tested corpora; a real collision would mis-parse and is easy to make more obscure if it ever matters.
  • Performance. The slotted runner is correctness-first; it is slower than egg on these inputs. Where the domain has no alpha-equivalence to exploit (e.g. nuts-bolts) it is pure overhead.
  • Operator matching is by display-name string (the slotted Symbol), where egg matched by typed discriminant. These agree because both come from the same Display, but it's a slightly stricter equality (byte-identical spelling) to keep in mind.

10. Validation tests (in src/seen_slotted.rs)

  • alpha_equivalent_metavars_collapse — (T ?#0 ?#1) makes (T ?#1 ?#0) a member, no rules.
  • relabelled_frozen_collapses — "first child frozen, second free" is one state regardless of labels.
  • frozen_vs_free_stays_distinct — frozen vs free at the same position stay distinct.
  • distinct_patterns_not_members — distinct top-level patterns (and interned subterms) are not members of each other.
  • dsr_saturation_merges — a scale-1 DSR makes a term and its scaled form equivalent after saturation.
  • commutativity_reordering_folds_via_alpha — (+ ?#0 ?#1) ≡ (+ ?#1 ?#0) with no rules (the sharing, part 1).
  • associativity_needs_dsr_not_alpha — reassociation comes from the DSR, not alpha; without the rule the bracketings stay distinct (the sharing, part 2 — no over-merging).
