TL;DR. The best-first search's seen-set had an experimental egraph side built on egg (over a frozen-var language, deciding dedup since it was the default decider). I replaced that egraph with a slotted e-graph (memoryleak47/slotted-egraphs), where a pattern's metavariables become slots, so alpha-equivalent patterns (the same shape with variables permuted — the blow-up that commutativity/associativity create) collapse natively, no rules needed. The corpus egraph is untouched (still egg), as requested. On nuts-bolts the new backend reproduces the egg results bit-for-bit: identical expansions (1185), identical egraph hits (657), identical final library (1.77×). It still beats the no-seen run. On a purpose-built commutative domain (§6½) the sharing does show: it cuts the search ~3.8× (82 vs 311 expansions) with an identical answer. All lib tests pass, including 7 in the new module that pin the encoding's semantics and the sharing.

1. What the seen-set is, and what I touched

Best-first abstraction search (src/best_first.rs) expands partial patterns. Many successors are redundant: the same search state reached by a different route. The seen-set (SeenTracker in src/search.rs) dedups them. It actually carried three parallel structures:

  • map — a hash map Pattern → freeze-mask with subset-domination. Cheap, syntactic.
  • dom_map — a never-evicted shadow of map for measuring how much domination buys.
  • the egraph side — each (pattern, freeze-mask) encoded as a term and looked up / inserted in an egg e-graph, with the domain rewrite rules (DSRs) run to saturation so dedup is modulo DSR-equivalence. This side was the default decider (--seen-egraph-decides, on by default).

This task replaces only the egraph side — the egg EGraph over the frozen-var language OpWithFrozenVar — with a slotted e-graph. The map/dom_map shadows stay (they're independent, cheap, and give the comparison the stats print). The corpus e-graph stays egg.

Why slotted, concretely. In the egg encoding a metavariable ?#k is a distinct constant leaf Var(k). So (+ ?#0 ?#1) and (+ ?#1 ?#0) are different egg terms; they only merge if a commutativity rule is present and saturated. In a slotted e-graph a metavariable is a slot, and the e-graph canonicalises terms up to a bijective renaming of slots — so those two collapse to one e-class at insertion time, with no rules. That native alpha-equivalence is the whole point: in domains with commutativity/associativity the search emits a pattern's variables in every order, and slotted folds them for free.

2. The encoding

The new backend is src/seen_slotted.rs. It defines one slotted Language and a handful of conversions. A pattern + its freeze mask becomes a slotted term like this:

  pattern          (T ?#0 ?#1)                with ?#0 frozen, ?#1 free
  slotted term     ($root$ (T (fpv $0) (pv $1)))
  • Non-frozen ?#k → a free slot, materialised as the leaf e-node (pv $k). Reuse of ?#k reuses slot $k, so variable sharing is preserved.
  • Frozen ?#k → (fpv $k) — the same slot $k under a distinct head. (See the judgement call below for why this is the right shape.)
  • Every operator → Op(symbol, children) — one variable-arity node carrying the operator name as a Symbol and its children as a Vec<AppliedId>. This is why one language covers an entire corpus whose operator set is only known at runtime.
  • The whole term is wrapped in Op($root$, [term]). add_expr interns every subterm, so without the wrapper a membership lookup would hit a pattern that merely occurs inside a larger inserted one. With it, a hit means the whole pattern was inserted as a top-level state. (This is the same trick the egg side used with its Root sentinel.)

DSRs are lifted onto this language (lift_rules_from_file) and run to saturation, so the e-graph dedups modulo DSR-equivalence on top of the alpha-equivalence it folds for free — matching the egg side's behaviour. Dedup itself is a membership check: build the $root$-wrapped term, and lookup_rec_expr it; present ⇒ skip, absent ⇒ insert (and, per the batch schedule, saturate).

3. Judgement calls

Frozen variables: (fpv $k), not renamed names and not a single tag chosen

You floated two options: distinct names like fx1, fx2, or a wrapper like (frozen x1). I used a wrapper-style head over the same slot: (fpv $k). The reasoning is a small case analysis of what "the same search state" must mean for frozen vars:

  • Frozenness must be structural so a frozen position never collapses with a free one: (T (fpv $0) (pv $1)) ≠ (T (pv $0) (fpv $1)) — different child is pinned, genuinely different states. The distinct head fpv vs pv gives exactly this.
  • Frozenness must still travel with the slot under renaming so two states that differ only by relabelling collapse: (T (fpv $0) (pv $1)) = (T (fpv $1) (pv $0)) (rename $0↔$1). Keeping the slot inside the fpv node gives this for free via slotted alpha-equivalence.
  • A frozen var must keep its identity for reuse / distinctness: (T ?#0 ?#0) (one frozen var twice) ≠ (T ?#0 ?#1) (two frozen vars). Because the slot lives inside the node, (T (fpv $0) (fpv $0)) ≠ (T (fpv $0) (fpv $1)) — preserved.

A single shared frozen tag (no slot) fails the third point; distinct names like fx1, fx2 fail the second (they'd need re-canonicalising to collapse relabellings). The slot-bearing distinct head satisfies all three. Tests relabelled_frozen_collapses and frozen_vs_free_stays_distinct pin this.

No binders — free slots at top level chosen

You noted the encoding "might look like a bunch of binds up at the top, or possibly no binds at all if free variables are allowed with no binder." Slotted e-graphs allow exactly that: an e-class simply has a set of public (free) slots; no lam/let binder is required to introduce them. So I use bare free slots and the $root$ wrapper just passes them through. No binders anywhere — the more convenient option, and it's what makes the alpha-equivalence "just happen" at add/lookup time.

Reused variables: nothing special needed confirmed

You expected reuse to be a non-issue, and it is. Index k maps to slot $k deterministically, so every occurrence of ?#k is the same slot and the sharing is preserved structurally. No special handling.

Membership, not e-class equality, is the dedup test important

A subtlety worth recording: in a slotted e-graph, (T (pv $0) (pv $1)) and (T (pv $1) (pv $0)) do share an e-class, but add_expr returns AppliedIds that bind the free slots in opposite orders, so an eg.eq(...) on those two applied-ids is false (they're different as applied terms). The operation the seen-set actually wants is "is an equivalent term present?", i.e. lookup_rec_expr on the canonicalised shape, which correctly returns hit. So contains() uses membership, never applied-id equality. (I learned this the hard way — see bug #2.)

Keep running the DSRs in the seen-egraph chosen

One could hope alpha-equivalence alone replaces the DSRs. It doesn't, in general: commutativity over structured arguments ((+ ?#0 (f ?#1)) ↔ (+ (f ?#1) ?#0)) is a real merge that alpha-equivalence does not make. And on nuts-bolts specifically the rules aren't commutativity at all — they're 7 scale-1 identities — so all the dedup there is DSR-driven. To faithfully replace the egg side (and to match its numbers) the slotted egraph runs the lifted DSRs to saturation, same as before. The alpha-equivalence is a bonus that simply doesn't fire on this no-commutativity domain.

Hand-written Language instead of define_language! chosen

The library's define_language! macro fixes each variant's arity and ties it to one operator-name string. A corpus has arbitrarily many operators of arbitrary arity, known only at runtime. So Op is a single variable-arity (Symbol, Vec<AppliedId>) variant, and I hand-write the Language impl — which is just the per-child chaining the macro would have generated, plus a from_syntax that dispatches on the head string (pv/fpv → slot leaves, anything else → operator).

Lift rules by string, skip what doesn't parse limitation noted

The rule file format (name: lhs => rhs, // comments, <=> bidirectional) and the slotted pattern syntax both use ?x metavariables and the same S-expression operator form, so rules lift almost verbatim. A rule whose sides don't parse as SeenLang — most importantly a lambda-calc rule using de-Bruijn $i, which the slotted parser reads as a slot — is skipped with a warning rather than crashing the run, and the count is surfaced. constant_folding directives are likewise skipped. This is the one real fidelity gap vs. the egg lifter (see §7); it does not affect nuts-bolts, whose rules are plain op-children rewrites.

Kept the whole SeenTracker interface and all CLI flags chosen

Every --seen-egraph-* flag still means what it meant: saturate, saturate-every, saturate-dynamic, decides. The dynamic batch-tuner's "did this flush dedup anything?" signal is reproduced faithfully — a freshly-inserted $root$ class that becomes multinode after a flush must have merged (by congruence) with another inserted root, since no rule mentions $root$. I dropped only --seen-egraph-node-limit from this path (the slotted runner is iteration-bounded, not node-bounded) and the egg-only search/apply/rebuild time breakdown from the audit print.

4. Bugs I hit (and fixed)

Bug #1 — node ordering. caused total search collapse
First run terminated after 18 expansions instead of 1185 — the egraph was reporting almost everything as already-seen. The dump was damning: (T ?#0 ?#1) was converting to just ($root$ (pv $1)) — operator and first child gone. Cause: I built pos_to_var from the pattern's own var-id table, but a pattern is stored as a RevExpr (root at index 0); converting it to an egg RecExpr reverses the node array and remaps child ids, so those ids no longer line up. Fix: detect variable leaves intrinsically via discriminant().as_var() and recover the index from a Var → k map — exactly what the old egg converter did. With that, every pattern converts to its full structure and the false hits vanish.
Bug #2 — eg.eq vs membership. While validating the encoding, my "alpha-equivalent patterns collapse" test failed on eg.eq(add(a), add(b)) even though the two were the same e-class. The returned applied-ids bind the shared free slots in opposite orders, so they differ as applied terms. The dedup the seen-set performs is membership (lookup_rec_expr), which canonicalises and correctly hits — so the test was wrong, not the encoding. Rewrote the tests around contains(), the real operation.

6. A domain where alpha-equivalence is the point (lambda-calc smoke test)

To check the lambda-calc path didn't regress, I ran basic-apps/multi-arg-assoc with its app-arith.rewrites — which are commutativity and associativity (plus_commut, plus_assoc, plus_merge, in curried @ form, no de-Bruijn, so all 6 lift cleanly). It saturates and returns a result: 468 expansions, 378 egraph hits, 4108 genuine inserts. This is the exact shape of redundancy slotted exists to fold.

This is also where the slotted saturation cost bites hardest: associativity+commutativity build large e-classes and the per-insert saturation ran ~2.7 s each (32 s total). The library's own benchmarks note assoc/comm add-chains can blow up. Two future levers for these domains: (a) drop the commutativity rule entirely and let native alpha-equivalence subsume it (a pattern's reordered variables are alpha-equivalent without any rule), and (b) the incremental-saturation work sketched in docs/seen_egraph_incremental_plan.html. Out of scope here — the goal was correctness, and that holds.

Two unit tests in src/seen_slotted.rs pin the equivalence exactly — that it shares what it should and nothing more:

7. Wall-clock: is it faster? (no — here's the full breakdown)

Worth being blunt: on both examples the slotted seen-set is not a wall-clock win. The alpha-equivalence advantage is real at the level of expansions (it folds the AC sharing — 82 vs 311), but that does not translate to wall-clock on these inputs. There are two different "slower than what?" questions with two different answers.

comm-demo (14 programs): slotted-seen vs no-seen — slower, because expansions here are nearly free

configexpansionstotalof which: egraph saturationeverything else
no seen-set3110.010 s— (no egraph)0.010 s
slotted (egraph decides)820.451 s0.431 s (96%)~0.020 s
map decides (egraph as shadow)3110.829 s0.771 s (93%)~0.058 s

The seen-set did its job — 82 vs 311 expansions — but look at what an expansion costs here: 0.010 s / 311 ≈ 32 µs. The corpus is tiny, so each expansion is nearly free; cutting 229 of them saves only ~0.007 s. To save that, the slotted egraph spent 0.43 s saturating the DSRs after inserts. Net ~0.44 s slower. The seen-set is an asymptotic optimization — it trades egraph bookkeeping for fewer expansions, and that only pays off once expansions are expensive enough. On a 14-program toy they aren't. (The "map decides" row is the worst case: it still builds and saturates the egraph as a shadow, so it pays the 0.77 s and runs all 311 expansions.)

nuts-bolts (250 programs): the seen-set does beat no-seen — but slotted is 3× the egg it replaced

configexpansionstotalegraph saturation
no seen-set10000 (budget)2.24 s—
slotted seen-set11850.92 s0.43 s
egg seen-set (before)11850.32 s0.012 s

Here the corpus is big enough that expansions are ~7× more expensive (2.24 s / 10000 ≈ 224 µs each) and there is a real blow-up (10000 → 1185). So the seen-set earns its keep: slotted-seen (0.92 s) is faster than no-seen (2.24 s). But it is 3× slower than the egg seen-set — identical 11 saturation flushes, identical dedup, but slotted saturation took 0.43 s vs egg's 0.012 s (~36× slower per flush).

Two root causes.
  1. The slotted e-graph's saturation engine is much slower than egg's (~36× per flush on nuts-bolts). It's a young library — a naive fixpoint loop, less-optimised e-matching/rebuild — and, like the egg version, it re-saturates the whole accumulated egraph on every flush (the cost docs/seen_egraph_incremental_plan.html targets). This is an implementation-maturity gap, not fundamental.
  2. The seen-set only beats no-seen when expansions are expensive and the blow-up is large. comm-demo has neither (tiny corpus, ~32 µs expansions), so the egraph overhead dominates no matter how good the engine is.

So what was delivered is a correct, behaviour-identical replacement that demonstrably folds the AC sharing — not a faster one. Levers that would flip the wall-clock trade, none done here: drop the commutativity rule and lean on native alpha (fewer/cheaper rules for the egraph to saturate); batch or incrementalise saturation; or run on a corpus large enough that the expansion blow-up dwarfs the egraph cost.

8. Limitations / things to know

  • Lambda-calc rules with de-Bruijn $i are skipped (the slotted parser reads $i as a slot). The run prints how many rules were dropped. For such domains the seen-egraph dedups by alpha-equivalence only, not by those rewrites. nuts-bolts and basic-apps are unaffected.
  • Reserved heads pv, fpv, $root$ would collide with a corpus operator spelled identically. None exist in the tested corpora; a real collision would mis-parse and is easy to make more obscure if it ever matters.
  • Performance. The slotted runner is correctness-first; it is slower than egg on these inputs. Where the domain has no alpha-equivalence to exploit (e.g. nuts-bolts) it is pure overhead.
  • Operator matching is by display-name string (the slotted Symbol), where egg matched by typed discriminant. These agree because both come from the same Display, but it's a slightly stricter equality (byte-identical spelling) to keep in mind.

  • Saturation is ~all of the search cost. 11.9 s of the 12.5 s search is per-insert saturation. Switch it off and search drops to 0.53 s.
  • Pure alpha-equivalence catches nothing here: saturation-off gets 0 egraph hits. The slotted backend's free win — folding variable permutations — simply never fires on this domain (see §12.4).

The remaining "few seconds" the request mentions — "the saturation that happens during printing of stats" — is the end-of-run audit. In the saturation-off run it is the dominant remaining cost: the audit saturates the accumulated 11717-enode egraph from scratch to report DSR-class counts, ~5 s (the 6.59 s total minus the 0.53 s search and ~1 s of load/startup). In the default run the audit's saturation is a no-op (already saturated) but the distinct-root-class recount still re-looks-up every inserted term twice.

Per-flush time is roughly linear in egraph size (~0.5–0.7 ms/enode), and the egraph grows ~linearly with inserts, so each flush is O(N) in the current size. Because flushes here land at doubling intervals, the cumulative is geometric and dominated by the last flush (5.7 s) — total ≈ 11.9 s. The dynamic batcher is what keeps this merely-bad rather than catastrophic: with --seen-egraph-saturate-every 1 (flush every insert) the same work becomes O(N²).

This is the "exponential feel," precisely. Saturation is not incremental: every flush re-runs all 70 rules against all classes, re-deriving the equivalences it already derived last flush plus the new batch's. As the search runs longer the egraph only grows, so each flush is strictly more expensive than the last. The last flush alone re-saturates a 9465-enode egraph (5.7 s) — and look at its effect: it adds 2222 enodes (the rules generating equivalent forms) while merging only 40 classes. Almost pure inflation.

12.3 Why slotted e-graphs can't save this domain

The hope was that slotted's native alpha-equivalence would absorb the blow-up. It can't, and the reason is in the rules. The molecule DSRs are two structural families, neither of which is variable-permutation:

reroot_s_1_2: (m1 ?e (s2 ?f ?y0)) <=> (m2 ?f ?y0 (s1 ?e))    // re-root the tree at a neighbour
comm_m2:      (m2 ?e ?n0 ?n1)      =>  (m2 ?e ?n1 ?n0)         // swap two neighbour SUBTREES
comm_s4_dup:  (s4 ?e ?n0 ?n1 ?n1)  =>  (s4 ?e ?n1 ?n0 ?n1)
rot_m4_a:     (m4 ?e ?n0 ?n1 ?n2 ?n3) => (m4 ?e ?n1 ?n2 ?n0 ?n3)
  • Re-rooting rewrites the whole tree shape (a different atom becomes the root). That is not an alpha-renaming of slots under any encoding — it must be a DSR.
  • Commutativity/rotation here is over structured arguments. The slotted free win folds (s4 ?#0 ?#1 ?#2) ≡ (s4 ?#1 ?#0 ?#2) — permuting bare slots. But the patterns the search actually inserts have structured children, e.g. (s4 C (s1 H) (s1 H) ?#0); commuting the two (s1 H) subtrees is a rewrite over subterms, which slotted does not canonicalise. It needs the comm DSR.

This is exactly why the saturation-off run scores 0 alpha hits: on molecules the redundancy lives in re-rooting and subtree-commutativity, the precise things slotted folds not for free. The slotted backend therefore offers no shortcut here — it falls back on running the same DSRs the egg backend would have, and those DSRs are what explode.

The sharper version (revises the §6½ interpretation). "Slotted folds commutativity for free" is only true for commuting bare variables — that case is literally a slot renaming ((+ ?x ?y) ≡ (+ ?y ?x); the commutativity_reordering_folds_via_alpha test is real). But in this search that capability is redundant with the search's own canonical variable numbering: Pattern::expand assigns metavar indices positionally, so the search never emits (+ ?#1 ?#0) as a state distinct from (+ ?#0 ?#1) — the cheap pattern map collapses them before the e-graph is consulted. So slotted's free alpha never gets two alpha-equivalent-but-distinct patterns to fold. I confirmed this with a control on the comm-demo (§6½) itself:
comm-demo configexpansionsegraph hits
slotted, saturation off (alpha only, no DSR)3110
map / no seen-set311—
slotted, saturation on (alpha + DSR)82(many)
With alpha alone the commutativity demo is back to 311 expansions, 0 hits — identical to no-seen. At insertion time the search's canonical numbering has already subsumed bare-variable permutation, so alpha folds nothing extra. The 311→82 win needs the comm/assoc DSRs to fire.
But — alpha does fire once the rules run (a correction). The "0 hits" above is the no-rules case. The moment saturation runs, the rewrites generate new terms, and when a comm/rot rule fires on a position holding free metavariables it produces genuine alpha-variants (permuted slots) — which slotted folds for free, whereas the old egg encoding (a distinct constant Var(k) per index, no slots) keeps them as distinct e-nodes. To measure this I added a third diagnostic, SEEN_VARS_AS_CONST (encode ?#k as a nullary op vK — egg-style, no slot, so alpha folds nothing), and ran it against the real encoding on the identical search walk (--no-seen-egraph-decides, so the map drives the search and the egraph is a shadow seeing the same 2586 calls):
encoding (identical walk)egraph dedup hitsgenuine insertsenodes after satdistinct root classes
real (slot-bearing; alpha active)156310235786653
SEEN_VARS_AS_CONST (egg-style; no alpha)13691217110131052
So slotted's native alpha is genuinely pulling weight during saturation: +194 dedup hits and a ~1.9× smaller egraph (5786 vs 11013 enodes; 653 vs 1052 root classes) than the egg encoding would produce on the same inserts. This is exactly the "once we run rewrite rules we will see them" effect — the rules manufacture the alpha-variants, and slots fold them for free.
…it just isn't enough, and doesn't even pay off in wall-clock. Two reasons it doesn't rescue molecules:
  1. The structural orbit dwarfs the alpha-foldable part. Alpha folds ~2× of the nodes, but the dominant blow-up is re-rooting (and comm over concrete atoms), which produces structurally-distinct terms alpha can't touch. After folding 2×, the egraph is still 5786 enodes and saturation still ~6 s.
  2. The 2× size win is eaten by slot overhead. Saturation here is 6.16 s (real) vs 5.88 s (egg-style) — essentially equal despite the real egraph having half the nodes. Slotted's slot-canonicalising e-matching/rebuild costs more per operation, so the smaller graph and the heavier per-node cost roughly cancel.

So the answer to "did we encode the rule wrong?" is no, and the answer to "does slotted help at all here?" is "yes, ~2× on egraph size via alpha during saturation — but it's swamped by the structural explosion and cancelled by slot overhead." There is no encoding that turns "swap two concrete sub-molecules" or "re-root the tree" into "rename a variable"; those are what dominate, and only the DSRs address them — and on molecules those DSRs explode regardless of how the variables are encoded.

Splitting the ruleset isolates the source. (Heavy caveat: --seen-egraph-decides means the seen-set steers the search, so changing the rules changes the trajectory and hence the insert counts — these rows are not the same walk. The signal that survives the confound is per-flush/relative cost, not absolute inserts.)

Neither family alone explodes; the cost is the interaction: re-rooting crossed with neighbour-permutation generates a large equivalence orbit per molecular pattern — every rooting × every neighbour ordering — and saturation materialises that whole orbit as e-nodes (the "+2222 enodes" we saw). Note also that reroot is what earns the good answer (2.63× vs comm-only's 2.08×): you can't simply drop it. The expense and the quality come from the same rules.

12.5 Encoding diagnostics: frozen costs nothing, variable-diversity costs ~3×

Per the request I added two diagnostic encoding toggles (env vars, read once; off by default — they change dedup semantics, so measurement-only). SEEN_NO_FROZEN drops the fpv head (frozen vars encoded like free ones); SEEN_UNIFY_VARS maps every metavar to the same slot $0, collapsing all variable identity. Default command, saturation on:

  • Variable diversity is a real ~3× factor. It keeps the same answer here, but it is unsound in general (it equates (T ?#0 ?#1) with (T ?#0 ?#0)), so it's a diagnostic, not a fix.
  • Both toggles together don't beat unify alone on time — variable diversity, not frozenness, is the size lever — and neither addresses the root cause (the reroot × comm orbit + whole-egraph re-saturation).

12.6 Why nuts-bolts doesn't blow up despite far more steps

The contrast is entirely in the rules. nuts-bolts has 7 scale-1 identities (§5) — each generates a tiny per-pattern orbit, so the seen-egraph stays small and its saturation totalled 0.012 s across the run. molecules has 70 reroot/comm/rot rules whose orbits are combinatorially large (§12.4). Same machinery, same whole-egraph re-saturation; the difference is how many equivalent forms the rules manufacture per inserted pattern. Step count is a red herring — it's orbit size per class.

12.7 Levers (none applied — this is a diagnosis)

  • Incremental saturation is the structural fix the per-flush curve points at: don't re-saturate the whole egraph each flush, only propagate from the newly inserted classes. This is what docs/seen_egraph_incremental_plan.html targets, and it's the one change that attacks the O(N)-per-flush re-derivation directly.
  • Recognise when slotted has nothing to add and skip saturation. On molecules the DSRs aren't alpha-equivalence, alpha hits are 0, and at this budget the answer is unchanged with saturation off — so --no-seen-egraph-saturate is 23× faster for the same result. (Budget-specific: at much larger budgets the DSR dedup may start to matter; the honest fix is making it cheap, not removing it.)
  • Make the stats audit cheap. ~7.7 s of the wall-clock is the end-of-run audit (a from-scratch saturation in the saturate-off case, a double distinct-root-class recount otherwise). It's pure reporting and could be gated behind a verbose flag.
  • Variable unification gives a free ~3× but is unsound in general; not a real option, only a measurement.

13. Sanity-check against the slotted e-graphs paper

The request (verbatim)
would you mind going and reading the slotted egraphs paper and making sure that what we've done here makes sense with respect to how these should actually be used? … i mean like everything weve done here.

I read the PLDI 2025 paper "Slotted E-Graphs: First-Class Support for (Bound) Variables in E-Graphs" (Schneider, Rossel, Shaikhha, Goens, Kœhler, Steuwer; 10.1145/3729326, open PDF) end-to-end, plus the library source we actually call (../slotted-egraphs/src/lang.rs, rewrite/mod.rs, run/runner.rs). Verdict up front: our implementation is a correct and idiomatic use of the library — every encoding decision lines up with the paper's model, and the API is used as intended. The honest caveat is not that we misused slotted, but that the library's signature strength (first-class bound variables) is largely orthogonal to where this seen-set's redundancy lives — which is exactly why §12 found it doesn't tame molecules.

13.1 What the paper says slotted e-graphs are for

  • The whole point is (bound) variables. Title and thesis: conventional e-graphs break sharing because "sub-terms that differ only in the names of their variables are represented separately," and the headline wins are avoiding de-Bruijn shifting / name-renaming duplication. Their big numbers are a λ-calculus fission benchmark where de-Bruijn encodings explode (egg-db: 1827k e-nodes, 5.1 GB) and slotted stays flat (214 e-nodes, 6 MB) — and two Mathlib theorems egg can't prove (one hits 2.6M e-nodes / 40 GB) that slotted proves in <1 s. All of that advantage is binder/α-driven.
  • Free slots without binders are first-class (Fig. 1): the e-class for a+b simply carries slots (e,f) with no binder. "e-classes are parameterized by the free variables of the terms they represent." So our "metavariables as bare free slots, no binders" encoding is exactly the supported model, not a hack.
  • Variable-commutativity is folded by a per-e-class symmetry group (Fig. 4), stored compactly via Schreier–Sims. a+b ≡ b+a becomes a slot permutation {(a,b),(b,a)} recorded on the class — not a duplicated e-node. Crucially this group is over slots (variables).
  • Redundant slots are dropped (Fig. 3): when y·0 = 0, slot y stops mattering and leaves the e-class's parameter list — handled automatically.
  • Slot overhead is intrinsic and acknowledged. §4.1: the same de-Bruijn encoding in slotted vs egg (slotted-db vs egg-db) is "2.7× more memory, and runs 7.8× slower … Part of this overhead is intrinsic to slots," plus the library is deliberately unoptimised ("we did not consider cache-friendliness, deferred rebuilding or compiled e-matching").

13.3 Is the saturation cost our fault or the library's model?

The §12.2 finding — every flush re-saturates the whole egraph — is inherent to the library, not our loop. Each apply_rewrites pass runs ematch_all(eg, lhs) for every rule, i.e. e-matches the full e-graph from scratch; there is no incremental "only the new classes" e-matching (the paper lists compiled e-matching among the optimisations it skipped). The Runner we could have used instead calls the identical core. So we are not leaving an incremental-saturation feature unused — the library doesn't have one. (An incremental seen-egraph would have to be built on top, which is what docs/seen_egraph_incremental_plan.html contemplates.)

13.4 The one real caveat: right tool, wrong axis of redundancy

Everything checks out mechanically, so the substantive question is whether a slotted e-graph is the right structure for this job at all. Reading the paper sharpens the §12 answer:

  • Slotted's superpower is α-equivalence of variables — folding terms that differ only by (bound/free) variable names, and folding variable-commutativity via the slot symmetry group. Its dramatic wins are all on binder-heavy, shift-heavy λ-calculus / theorem-proving workloads.
  • This seen-set has no binders and few metavariables per pattern, and the search already canonical-numbers them. So the regime where slotted shines (lots of variable renaming/shifting) barely occurs. The measured benefit is the narrow slice in §12.3: alpha folding rule-generated variants, ~1.9× on egraph size — real, but small, and cancelled by the intrinsic slot overhead the paper quantifies (2.7×/7.8×).
  • The molecules blow-up is on an axis slotted fundamentally can't address. Re-rooting reshapes the tree and commutativity is over structured subterms; neither is a slot permutation, so neither the congruence-modulo-renaming nor the symmetry-group machinery applies. The paper's model makes this crisp: symmetry groups permute slots, not subterm children — so there is no encoding within slotted's model that turns "swap two sub-molecules" or "re-root" into "rename a variable." (The sort-children canonicalisation floated earlier lives outside the e-graph, precisely because slotted can't express it.)
Bottom line. We built the slotted seen-set the way the paper and library intend: free slots for metavariables, no binders, a hand-written variable-arity Language whose shape/slot methods match the contract, membership-based dedup, and idiomatic saturation. Nothing here is a misuse. The reason it under-delivers on molecules is not a wrong encoding — it's that slotted e-graphs are built to make bound variables first-class, and this domain's redundancy is structural rewriting (re-rooting) plus commutativity over concrete subterms, which is orthogonal to what slotted accelerates. Where the domain's redundancy is α-shaped, our usage does capture it (§12.3); it's simply not the dominant cost here.
