Plan A — Incremental seen-egraph saturation

Design note for making per-insert DSR saturation of the best-first seen-egraph cheap. Benchmark throughout: nuts_bolts_enum (op-children, 7 scale DSRs, --opt-seen, egraph decides).

TL;DR. The cost is not e-matching and not rebuild — it's rule application (73%), because each genuine insert re-saturates the whole accumulated egraph from scratch and re-applies every old match as a no-op. Batching (Plan B, already shipped) is a 25–47× free win with zero precision loss up to --seen-egraph-saturate-every 64 here. Plan A (incremental) is the asymptotic fix: touch only the new term's neighbourhood. The hard part is correctly tracking the upward dirty cascade that rebuild + congruence produce. Recommend: run with batching now; build A only if eager (every=1) exactness is needed cheaply or larger corpora erode the batching window.

2. Root cause

Every genuine insert does Runner::default().with_egraph(take(seen_egraph)).run(&rules): a fresh, from-scratch saturation of the entire accumulated egraph. The egraph grows to ~4600 enodes / 3072 classes, and the scale rules match essentially every T/C/repeat/leaf node, so each call re-finds and re-applies ~O(egraph) matches that were already at fixpoint. Cost per insert grows with egraph size ⇒ the run is ~O(inserts × egraph_size) ≈ O(n²). The flat 1.5 ms average hides that late saturations are far more expensive than early ones.

3. Plan A — the idea

Keep one persistent, already-saturated seen-egraph. On insert, don't re-saturate globally — only propagate rules through the region the new term disturbs. After a fixpoint, the only rule matches that can newly fire are those whose match touches a newly-added or newly-merged enode; everything else is unchanged and already saturated. So we run a local worklist to a fixpoint instead of a global runner.

seed = classes/enodes created by add_expr(new term)
dirty = seed
while dirty not empty:
    # 1. find only the NEW matches: rules rooted at dirty classes AND at
    #    their ancestors up to the rule-LHS height (see §4 — matches can be
    #    rooted above a changed class).
    matches = []
    for c in dirty ∪ ancestors(dirty, up to maxLhsHeight):
        for rw in rules:
            matches += rw.searcher.search_eclass(egraph, c)   # local e-match
    # 2. apply only those; record union targets + RHS-introduced enodes
    changed = apply(matches)            # unions + new enodes
    # 3. congruence repair; capture everything it touched (see §4)
    merged = egraph.rebuild_tracking_changes()
    # 4. re-seed: new enodes, merged classes, and their parents are dirty
    dirty = (changed.new_enodes ∪ merged ∪ parents(merged)) not already settled
# egraph is saturated again; membership lookups are exact modulo DSR-equiv

4. The dirty cascade — does it propagate to parents? (yes, two ways)

This is the crux the plan lives or dies on. There are two upward propagation mechanisms, both confirmed in egg's source.

(a) Congruence cascade during rebuild

When two classes merge, perform_union does self.pending.extend(class2.parents.iter().copied()). process_unions then re-canonicalizes each parent enode and looks it up in the memo; if a parent becomes congruent to an existing enode, it merges too — pushing its parents, and so on. So a single child-level union can ripple arbitrarily far up the DAG. egg handles this internally and correctly; the catch is that the set of classes it merged is not returned (only a union count), and we need that set to know what became dirty.

(b) Rule-rematch cascade — matches rooted above a change

e-matching is rooted: a match for (T ?x ?m) is anchored at the T enode, with the changed class possibly filling ?x one level below the root. So when class c gains an enode, new matches can appear rooted at c and at any ancestor within the rule's LHS height. Searching only "rooted at c" misses them. Therefore the search frontier must include ancestors(dirty, up to maxLhsHeight). For these DSRs LHS height ≤ 2, so the radius is tiny; in general it's bounded by the tallest LHS.

Direction of the cascade. It only goes up. Merging a parent does not change any child's canonical id, and bottom-up e-matching of a child never depends on its parent — so children never become dirty from above. The frontier is: new enodes (from add_expr and from applied RHSs) ∪ merged classes ∪ their parents-within-LHS-height. Apply introduces fresh RHS enodes (e.g. l ⇒ (T l (M 1 0 0 0)) adds a (T l …) node), which re-seed the loop exactly like normal saturation — so the local loop still reaches the global fixpoint, just without revisiting the untouched bulk.
      ?               parents re-canonicalized → may merge (congruence) ↑
      |                                                                 |
   (T · m)   ← new match rooted here can fire because child changed ----+
      |
   [ l ]  ← add (T l (M 1 0 0 0)); l-class gains an enode  (SEED, dirty)
            apply introduces (T l (M..)) and (M 1 0 0 0)   (new enodes, dirty)

5. egg API reality & the hard part

  • Local search exists: Searcher::search_eclass(&egraph, id) returns matches of a pattern rooted at one eclass — the primitive we need for step 1.
  • Apply at a site: drive rw.applier per match (or build substs and union manually) instead of Runner, which only does global passes.
  • The hard part — observing what rebuild merged. EGraph::rebuild() returns only n_unions, and the congruence-cascade merges happen inside it. Options:
    1. Snapshot canonical ids of candidate classes before/after rebuild and diff (simple, O(touched)).
    2. Drive unions ourselves and call rebuild in small steps, reading find() deltas.
    3. Small egg patch: have rebuild also return/record the set of merged roots (cleanest, but forks egg further — we already run a patched egg, so this is on the table).
    We can over-approximate safely using the public EClass::parents field to walk the upward frontier; over-approximation only costs extra (harmless) re-search, never correctness.

6. Correctness argument

Invariant: after each insert the seen-egraph equals what a full run(&rules) would produce (same classes, same congruence closure). Proof sketch: assume it held before the insert (egraph saturated). add_expr changes only the new term's nodes. A rule instance can newly fire only if its match touches a changed enode; all such instances are reachable by searching the dirty set ∪ ancestors-within-LHS-height (§4b). Applying them and repairing congruence (§4a) reaches a local fixpoint; because every newly-enabled instance is considered and the untouched region was already a fixpoint, the local fixpoint equals the global one. ∎

Cheap guard: in debug builds, every K inserts run a full saturate() into a clone and assert identical number_of_classes() / membership — catches an LHS-height or dirty-set bug fast. (Note this guard does clone, unlike the hot path, which never does.)

7. Expected payoff & risks

  • Asymptotics: per-insert cost O(egraph_size) → O(disturbed region) ≈ O(term size × local fan-out). Should turn the 2.1 s into low-ms territory and remove the O(n²) back-loading.
  • vs batching: Plan B already buys ~25× for ~10 lines and zero precision loss here. A and B are complementary (B = fewer saturations, A = cheaper saturations). A's marginal value: cheap eager (every=1) exactness, and corpora big enough that the batching window starts dropping real dedups.
  • Risk — LHS-height radius: too small ⇒ silent under-saturation. Mitigate with the debug full-saturation guard and by computing the radius from the actual parsed rules, not a constant.
  • Risk — rebuild change-set: the main implementation effort; needs the diff/patch from §5. Until then a hybrid (incremental search + occasional full rebuild) is possible.
  • Interaction with batching: if both are on, the "already saturated" precondition is false; seed the dirty set with all pending-batch terms before running the local fixpoint.

8. Recommendation / sequencing

  1. Ship Plan B now (done): --seen-egraph-saturate-every. Default could move from 1 to a small N once we confirm the no-precision-loss window on other corpora.
  2. Keep SimpleScheduler; add a stop_reason == Saturated assertion if we ever change scheduler/limits.
  3. Prototype Plan A behind a flag (--seen-egraph-incremental) using search_eclass + manual apply + the before/after canonical-id diff for the change-set, validated by the debug full-saturation guard. Measure against batching to decide if the extra machinery earns its keep.
